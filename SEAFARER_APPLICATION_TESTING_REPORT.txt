ISSUE #1 — COMPREHENSIVE SEAFARER ONBOARDING FAILED
================================================================================

ID:           SEA-001
Severity:     Critical
Status:       Failed
Module:       Onboarding → Seafarer comprehensive onboarding
UI route:     /onboarding/seafarer/setup (SeafarerOnboardingForm)
API:          POST /seafarer/api/v1/.../onboarding/comprehensive
              (via submitComprehensiveOnboarding in comprehensive-onboarding-service.ts)

Description:
  Submitting the full seafarer comprehensive onboarding form fails. The
  transaction is rolled back on the server; no seafarer record is persisted.

Steps to reproduce:
  1. Log in as a user completing seafarer onboarding.
  2. Navigate to seafarer onboarding setup and complete all required sections
     (contact, education, training, voyage, documents, etc.).
  3. Submit the comprehensive onboarding form.

Expected result:
  HTTP 200/201 with success payload; onboarding completed; user can proceed
  in the application.

Actual result:
  HTTP 400 with generic failure response.

API response (observed):
  {
    "apiVersion": "v1",
    "success": false,
    "code": "400",
    "message": "Unsuccessful.",
    "requestId": null,
    "data": null,
    "error": {
      "message": "An error occurred during comprehensive onboarding. All changes have been rolled back.",
      "code": "ONBOARDING_FAILED"
    }
  }

Frontend notes:
  - Submission is implemented in SeafarerOnboardingForm.tsx via
    submitComprehensiveOnboarding().
  - The frontend surfaces the API error; the failure originates on the backend
    during the transactional comprehensive onboarding operation.

Recommended actions:
  - Backend: Inspect server logs for the specific exception behind
    ONBOARDING_FAILED (validation, FK constraints, file upload, IMS sync, etc.).
  - QA: Capture requestId when available; retry with minimal required fields to
    isolate failing section.
  - DevOps: Confirm dev API and storage (document upload) are healthy.

ISSUE #2 — SEAFARER EMPLOYER ONBOARDING FAILED (PERMIT VERIFICATION)
================================================================================

ID:           SEA-002
Severity:     Critical
Status:       Failed
Module:       Onboarding → Seafarer Employer (Agent)
UI route:     /onboarding/verify-identity → Agent onboarding flow
API:          GET /verify/permit/{permitNumber}/service-type/SEAFARER_EMPLOYER
              (permit-validation-service.ts → NEXT_PUBLIC_PERMIT_VERIFY_BASE_URL)

Description:
  Onboarding as a Seafarer Employer cannot proceed because permit verification
  returns an internal server error before employer onboarding can complete.

Steps to reproduce:
  1. Start employer (agent) onboarding.
  2. Enter permit number (e.g. PERMIT-TRAINING_INSTITUTIONS-2026-000001 or
     employer permit as applicable).
  3. Submit permit verification for service type SEAFARER_EMPLOYER.

Expected result:
  Permit validated; user proceeds to employer onboarding steps.

Actual result:
  HTTP 500 Internal Server Error.

API response (observed):
  {
    "type": "https://api-dev.mems.ng/errors/INTERNAL/SERVER_ERROR",
    "title": "Internal Server Error",
    "status": 500,
    "detail": "no pg_hba.conf entry for host \"10.0.11.162\", user \"mems\", database \"mems\", no encryption",
    "instance": "/verify/permit/PERMIT-TRAINING_INSTITUTIONS-2026-000001/service-type/SEAFARER_EMPLOYER",
    "code": "INTERNAL/SERVER_ERROR",
    "correlationId": "req-1778849496726-0pkiy5w4n",
    "timestamp": "2026-05-15T12:51:36.726Z"
  }

Root cause (inferred):
  PostgreSQL client host 10.0.11.162 is not allowed in pg_hba.conf for user
  "mems" on database "mems" without SSL. This is an infrastructure / database
  configuration issue on api-dev, not a frontend logic defect.

Frontend notes:
  - validatePermit() in permit-validation-service.ts calls the external verify
    endpoint; the UI correctly displays failure when the API returns 500.

Recommended actions:
  - DevOps/DBA: Add pg_hba.conf entry for application host 10.0.11.162 (or
    require SSL and configure client accordingly).
  - Backend: Ensure permit verification service can reach PostgreSQL in dev.
  - QA: Re-test after infra fix; confirm correct permit prefix for employer
    (PERMIT-SEAFARER_EMPLOYER-...) vs training institution permit used in test.

ISSUE #6 — SEAFARER PROFILE DOCUMENT DOWNLOAD NOT RESPONSIVE
================================================================================

ID:           SEA-006
Severity:     High
Status:       Failed
Module:       Seafarer Management → Seafarer Profile → Document tab
UI route:     /seafarer/profile/[id]  (e.g. /seafarer/profile/SEA-2026-0057)

Description:
  On the Seafarer Profile page, Document tab, each uploaded document shows a
  Download button that does nothing when clicked.

Steps to reproduce:
  1. Log in (e.g. as employer or admin with access to seafarer profiles).
  2. Open My Seafarers / registry and open a seafarer profile.
  3. Select the “Document” tab.
  4. Click Download on any listed document (Passport, CDC, Medical, etc.).

Expected result:
  File downloads or opens in a new tab from document storage URL.

Actual result:
  No action, no download, no error message.

Frontend root cause (confirmed in code):
  - File: src/app/(dashboard)/seafarer/profile/[id]/page.tsx
  - Documents are hardcoded mock data (static array, not from API).
  - Download <Button> has no onClick handler and no href.
  - Profile page is largely placeholder UI (mock licenses, employment, John Doe).

Contrast:
  - Working download pattern exists in profile-documents/page.tsx and
    admin/applications/review/page.tsx (handleDownloadDocument with fetch/blob).

Recommended actions:
  - Frontend: Wire profile page to real seafarer/document API; implement
    handleDownloadDocument consistent with profile-documents page.
  - Backend: Expose document list + signed URL or file path for profile by RN/id.
  - Replace mock profile data with API-driven seafarer detail.

ISSUE #7 — ONBOARD SEAFARER (EMPLOYER) NOT GOING THROUGH
================================================================================

ID:           SEA-007
Severity:     Critical
Status:       Failed
Module:       Seafarer Management → Onboard Seafarer (employer on behalf of)
UI route:     /seafarer/add
API:          Intended: create seafarer record (employer-initiated registration)
              Current: createSeafarer() in lib/services/seafarers.ts

Description:
  Seafarer employers cannot onboard a new seafarer via “Onboard Seafarer” in the
  sidebar (Seafarer Management → Onboard Seafarer).

Steps to reproduce:
  1. Log in as Seafarer Employer.
  2. Navigate to Onboard Seafarer (/seafarer/add).
  3. Complete User Information form and submit.

Expected result:
  Seafarer created in registry; redirect or success confirmation.

Actual result:
  Submission does not complete successfully (user report: “not going through”).

Frontend root cause (confirmed in code):
  - add/page.tsx calls createSeafarer(payload) from @/lib/services.
  - createSeafarer() is explicitly DEPRECATED and stubbed: it does NOT call the
    network and always returns:
      success: false
      error.code: "ENDPOINT_NOT_FOUND"
      error.message: "Endpoint /api/Seafarers does not exist in the API"
  - Comment in seafarers.ts: legacy /api/Seafarers returns 404; not in swagger.

Recommended actions:
  - Frontend: Point /seafarer/add to the correct supported API endpoint from
    current swagger (e.g. seafarer registry/onboarding API used elsewhere).
  - Backend: Confirm canonical endpoint for employer-initiated seafarer creation.
  - Remove or replace deprecated stub so users get a clear error if API is missing.
  - Align with comprehensive onboarding or simplified create flow per product spec.
